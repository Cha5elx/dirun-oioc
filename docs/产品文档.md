# DiRun OIOC 产品文档

## 一、产品概述

### 1.1 产品定位

DiRun OIOC 是一个**中间件同步服务**，连接**有赞商城**与**第三方一物一码系统**，实现库存、订单、防伪码的自动双向同步。

```
有赞商城 ←── Webhook/API ──→ 本服务 ←── Webhook/API ──→ 第三方一物一码系统
  (销售渠道)                   (数据桥梁)                   (溯源管理)
```

### 1.2 核心价值

| 价值 | 说明 |
|------|------|
| **自动化** | 入库自动加库存、出库自动发货扣库存，全程无需人工操作 |
| **防伪溯源** | 每件商品绑定唯一防伪码，消费者可扫码验真伪、查来源 |
| **零差错** | 幂等性保护 + 失败重试队列，确保数据不丢不重 |
| **可观测** | 同步日志、重试队列统计、健康检查，运维状态一目了然 |

### 1.3 用户角色

| 角色 | 操作入口 | 职责 |
|------|---------|------|
| **仓库管理员** | 第三方一物一码系统 | 扫码入库、扫码出库、扫码退货 |
| **商家运营** | 有赞商家后台 + 本服务管理后台 | 查看订单、管理商品映射、监控同步状态 |
| **消费者** | 微信/支付宝扫码 | 查询防伪码、验真伪、看溯源 |
| **系统管理员** | 本服务管理后台 | 用户管理、日志管理、系统配置 |

## 二、功能清单

### 2.1 核心业务流程

| 流程 | 触发方 | 说明 | 状态 |
|------|--------|------|------|
| **商品采购入库** | OIOC Webhook | 仓库扫码入库 → OIOC推送 → 有赞自动加库存 | ✅ |
| **销售发货** | 有赞 Webhook → OIOC Webhook | 用户下单 → 创建出库单 → 扫码发货 → 有赞自动发货+扣库存+写防伪码 | ✅ |
| **退货退款** | 有赞 Webhook → OIOC Webhook | 用户退货 → 创建退货单 → 扫码退货 → 有赞自动恢复库存 | ✅ |

### 2.2 管理后台功能

| 页面 | 功能 | 权限 |
|------|------|------|
| **数据仪表盘** | 今日订单/入库/出库/退货统计 | operator |
| **同步日志** | 查看所有同步操作记录，支持按类型/状态/时间筛选 | operator |
| **有赞订单** | 查看有赞订单列表和详情 | operator |
| **一物一码订单查询** | 输入订单 ID 查询该订单对应的条码信息（对接 `/barcodes/get_by_order/{orderID}`） | operator |
| **产品管理** | 创建和查询 OIOC 产品，支持分页和筛选，支持从有赞商品批量导入 | operator |
| **代理管理** | 创建和查询 OIOC 代理（必填：代理ID、账号、密码、用户类型、父级ID），支持分页 | operator |
| **一物一码单据** | 创建和查询入库单/出库单/退货单，支持条码查询 | operator |
| **用户管理** | 创建/编辑/删除用户，角色分配 | admin |
| **产品映射** | 管理有赞商品SKU与OIOC产品编码的映射关系 (API) | admin |

### 2.3 系统保障机制

| 机制 | 说明 |
|------|------|
| **幂等性保护** | 基于业务键 + 数据指纹的重复请求检测，防止重复入库/发货 |
| **失败重试队列** | API 调用失败自动入队，指数退避重试（30s → 60s → 120s），最多3次 |
| **签名验证** | Webhook 接收时验证 HMAC-SHA256 签名，防止伪造请求 |
| **速率限制** | 普通 API 和 Webhook 独立限流，防止滥用 |
| **日志清理** | 定时清理过期日志（默认保留30天/10000条），自动 VACUUM 数据库 |
| **数据库自动备份** | 每次清理前自动备份 SQLite 数据库文件到 `database/backups/` |
| **Token 管理** | OIOC Token 自动缓存和刷新，有赞 Token 免登续期 |
| **Dry Run 模式** | `YOUZAN_DRY_RUN=true` 时跳过有赞写操作（库存加减、发货、备注），保留查询类 API 真实调用 |

## 三、系统架构

### 3.1 技术栈

| 层 | 技术 |
|----|------|
| **后端运行时** | Node.js 18+, Koa 3.x |

### 3.3 数据流图

```
流程1 — 入库:
  OIOC 系统 ─POST /webhook/oioc {type:"inbound"}─→ webhook.js
    → sync.handleInbound()
      → oioc.login()
      → oioc.createInboundOrder()     (在OIOC创建入库单)
      → youzan.addStock()              (有赞加库存)
      → syncLog.create()               (记录日志)

流程2 — 发货:
  有赞 ─POST /webhook/youzan {type:"trade_TradePaid"}─→ webhook.js
    → sync.handleOrderCreated()
      → youzan.getOrder()             (获取订单详情)
      → oioc.login()
      → oioc.createOutboundOrder()    (在OIOC创建出库单)
      → syncLog.create()

  OIOC ─POST /webhook/oioc {type:"outbound"}─→ webhook.js
    → sync.handleOutbound()
      → youzan.subtractStock()        (有赞扣库存)
      → youzan.shipOrder()            (有赞标记发货)
      → youzan.updateOrderRemark()    (写入防伪码到备注)
      → syncLog.create()

流程3 — 退货:
  有赞 ─POST /webhook/youzan {type:"trade_TradeRefundCreated"}─→ webhook.js
    → sync.handleRefund()
      → oioc.createReturnOrder()      (在OIOC创建退货单)

  OIOC ─POST /webhook/oioc {type:"return_complete"}─→ webhook.js
    → sync.handleReturnComplete()
      → youzan.addStock()             (有赞恢复库存)

失败处理:
  任意流程失败 ──→ retryQueue.enqueue()
    → 每15秒轮询 → 30s/60s/120s 指数退避重试 → 最多3次
```

## 四、API 参考

### 4.1 Webhook 端点

| 方法 | 路径 | 说明 | 签名验证 |
|------|------|------|---------|
| POST | `/webhook/youzan` | 接收有赞事件推送 | ✅ HMAC-SHA256 |
| POST | `/webhook/oioc` | 接收 OIOC 事件推送 | ✅ HMAC-SHA256 |
| GET | `/health` | 健康检查 | 无 |

#### 有赞事件类型

| type | 处理函数 | 说明 |
|------|---------|------|
| `trade_TradeCreated` | `handleOrderCreated()` | 订单创建 |
| `trade_TradePaid` | `handleOrderCreated()` | 订单付款 |
| `trade_TradeRefundCreated` | `handleRefund()` | 退货申请 |

#### OIOC 事件类型

| type | 处理函数 | 说明 |
|------|---------|------|
| `inbound` | `handleInbound()` | 商品入库 |
| `outbound` | `handleOutbound()` | 商品出库（发货） |
| `return_complete` | `handleReturnComplete()` | 退货完成 |

### 6.2 服务器首次部署

项目提供 `scripts/deploy-server.sh` 一键部署脚本，自动完成以下全部步骤。

**前置条件**：一台 Linux 服务器（CentOS 7+ / Ubuntu 18+），root 或 sudo 权限。

#### 方式一：脚本一键部署

```bash
# 1. 在服务器上下载部署脚本
wget https://raw.githubusercontent.com/Cha5elx/dirun-oioc/main/scripts/deploy-server.sh

# 2. 执行部署
sudo bash deploy-server.sh
```

脚本自动完成：
1. 安装编译工具（gcc、python3，编译 sqlite3 原生模块需要）
2. 安装 Node.js 18（通过 nvm）
3. 安装 PM2（全局）
4. 安装 Nginx（可选）
5. 克隆项目代码到 `/opt/dirun_oioc`（public/ 已包含预构建的前端资源）
6. 安装后端依赖（`npm install`），前端无需在服务器构建
7. 配置 `.env` 环境变量
8. 配置防火墙（开放 80/443/3000 端口）
9. 使用 PM2 启动服务，设置开机自启
10. 配置 Nginx 反向代理（可选）
11. 健康检查

#### 方式二：手动部署

```bash
# 1. 安装 Node.js 18（通过 nvm）
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash
source ~/.bashrc
nvm install 18
nvm use 18
nvm alias default 18

# 2. 安装 PM2
npm install -g pm2

# 3. 克隆项目（public/ 已包含本地预构建的前端资源）
sudo mkdir -p /opt
cd /opt
git clone https://github.com/Cha5elx/dirun-oioc.git
cd dirun_oioc

# 4. 安装后端依赖（前端无需在服务器构建）
npm install

# 5. 配置环境变量
cp .env.example .env
vi .env    # 填入有赞和 OIOC 的真实配置

# 6. 使用 ecosystem.config.js 启动（推荐）
pm2 start ecosystem.config.js --env production

# 7. 设置 PM2 开机自启
pm2 startup
pm2 save

# 8. 验证
curl http://localhost:3000/health
```

#### PM2 配置说明 (`ecosystem.config.js`)

项目根目录已包含 PM2 配置文件：

```javascript
module.exports = {
  apps: [{
    name: 'dirun-oioc',
    script: './index.js',
    instances: 1,               // 实例数，设为 'max' 可启用集群模式
    autorestart: true,          // 崩溃自动重启
    watch: false,               // 生产环境不监听文件变化
    max_memory_restart: '256M', // 内存超过 256MB 自动重启
    env_production: {
      NODE_ENV: 'production',
      PORT: 3000
    },
    log_date_format: 'YYYY-MM-DD HH:mm:ss',
    error_file: './logs/error.log',
    out_file: './logs/out.log',
    merge_logs: true,
    min_uptime: '10s',          // 最小运行时间，防止频繁重启
    max_restarts: 10,           // 最大异常重启次数
    restart_delay: 4000         // 重启间隔 4 秒
  }]
};
```

#### Nginx 反向代理

```nginx
# /etc/nginx/conf.d/dirun-oioc.conf
server {
    listen 80;
    server_name your-domain.com;

    # 静态文件缓存
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff|woff2|ttf|eot)$ {
        proxy_pass http://127.0.0.1:3000;
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # API 和页面
    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_cache_bypass $http_upgrade;
        # 延长超时，避免长耗时同步请求被切断
        proxy_read_timeout 120s;
        proxy_send_timeout 120s;
    }
}
```

配置完成后：

```bash
sudo nginx -t                    # 验证配置
sudo systemctl restart nginx     # 重启 Nginx
sudo certbot --nginx -d your-domain.com  # 配置 SSL（推荐）
```

### 6.3 服务器更新

#### 更新流程概览

```
本地构建前端 → git push → 服务器 git pull → 安装后端依赖(如有变化) → 重启服务 → 健康检查
```

> **关键设计**：`public/` 目录已提交到 Git，服务器 `git pull` 后直接使用预构建的前端资源，**无需在服务器上安装前端依赖或执行构建**。

#### 方式一：脚本更新（推荐）

使用 `scripts/update-server.sh` 一键更新，脚本会自动备份、拉取代码、更新依赖、重启和健康检查：

```bash
cd /opt/dirun_oioc
bash scripts/update-server.sh
```

脚本执行流程：
1. 备份当前数据库文件
2. 备份整个项目目录
3. 对比 `package.json` 变化，决定是否重新编译原生模块
4. 拉取最新代码（交互确认），前端资源随代码一并拉取
5. 更新后端依赖
6. 重启服务 + 健康检查（3 次重试）
7. 健康检查失败时提示回滚命令

#### 方式二：PM2 不停机更新（零停机）

**原理**：PM2 的 `reload` 命令在集群模式下逐个重启实例，始终保持至少一个实例在线。

```bash
# 第一步：首次部署时开启集群模式（2 个实例）
pm2 start ecosystem.config.js --env production -i 2
# 或修改 ecosystem.config.js 中 instances: 2 后执行 pm2 start ecosystem.config.js

# 第二步：后续更新使用 reload 实现零停机
cd /opt/dirun_oioc
git pull                          # 拉取代码和预构建的前端资源
npm install                       # 有依赖变化时
pm2 reload dirun-oioc             # 零停机重启

# 验证
pm2 status
curl http://localhost:3000/health
```

**reload vs restart 对比**：

| 操作 | 命令 | 停机时间 | 适用场景 |
|------|------|---------|---------|
| `reload` | `pm2 reload dirun-oioc` | 0 秒（需 instances >= 2） | **生产更新，推荐** |
| `restart` | `pm2 restart dirun-oioc` | 2~5 秒 | 单实例、紧急重启 |

> **建议**：生产环境将 `instances` 设为 2 或 `'max'`，日常更新使用 `pm2 reload`，实现用户无感知的不停机更新。

#### 方式三：手动更新（单实例）

```bash
cd /opt/dirun_oioc

# 1. 备份数据库
cp database/dirun.db database/backups/dirun.db.$(date +%Y%m%d_%H%M%S)

# 2. 拉取代码（前端资源已预构建在 public/ 中，随代码一并拉取）
git pull

# 3. 更新后端依赖
npm install

# 4. 重启服务
pm2 restart dirun-oioc

# 5. 健康检查
sleep 3
curl http://localhost:3000/health
```

#### 回滚方法

如果更新后出现问题，使用更新前自动创建的备份回滚：

```bash
# 恢复项目目录（BACKUP_DIR 在脚本输出中显示）
sudo cp -r /opt/backups/dirun_oioc_20260429_143000/* /opt/dirun_oioc/
pm2 restart dirun-oioc

# 或从 Git 回滚
cd /opt/dirun_oioc
git revert <commit-hash>
pm2 restart dirun-oioc
```

#### 仅更新前端（无需重启后端）

前端更新在**本地**完成构建，再推送到服务器：

```bash
# === 本地操作 ===
cd admin
npm run build                    # Vite 输出到 ../public/
cd ..
git add public/ admin/src/
git commit -m "update frontend"
git push

# === 服务器操作 ===
cd /opt/dirun_oioc
git pull                         # 拉取已构建的 public/ 资源
# 后端静态文件服务自动生效，无需重启
```

### 7.7 常见问题排查

| 问题 | 排查步骤 |
|------|---------|
| 服务无法启动 | 1. 检查 `.env` 必填项是否完整 2. `netstat -tlnp \| grep 3000` 检查端口 3. 确认 sqlite3 原生模块编译成功 |
| Webhook 收不到 | 1. 确认回调 URL 可公网访问 2. 检查 `YOUZAN_SIGN_SECRET` / `OIOC_SIGN_SECRET` 配置 3. 开发环境会自动跳过签名验证 |
| 同步失败 | 1. 查看 `/api/logs?status=failed` 2. 检查重试队列 `/api/retry-queue/stats` 3. 查看 `pm2 logs dirun-oioc --err` |
| 库存不一致 | 1. 筛选 `inbound` / `outbound` 类型日志核对 2. 确认产品映射关系正确 `/api/product-mappings/search` |
| 登录失败 | 1. 确认 OIOC 第三方系统账号密码正确 2. 确认 `OIOC_BASE_URL` 可连通 |
| PM2 频繁重启 | 1. `pm2 show dirun-oioc` 查看重启次数 2. 检查是否达 `max_restarts: 10` 上限 3. `pm2 logs dirun-oioc --err` 定位崩溃原因 |
| 数据库文件过大 | 1. `/api/logs/stats` 查看大小 2. `/api/logs/cleanup` 手动清理 3. 减小 `daysToKeep` 或 `maxLogCount` 参数 |
| EPIPE/ECONNRESET 错误 | 正常现象（客户端提前断开），已在全局异常处理中忽略，不影响服务运行 |
